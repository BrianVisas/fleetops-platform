# Phase 4 — Kubernetes and GitOps (local)

Goal: FleetOps runs on a local Kubernetes cluster, and the cluster is driven by
git. Merging a change to `main` ends with the new version running in `dev`,
proven by a smoke test, with nobody running `kubectl`. Promotion to the next
environment is a pull request, and a rollback is a revert. Release `v0.4.0`.

## Work packages

| # | Branch | Delivers |
|---|--------|----------|
| 1 | `infra/1-kind-cluster` | `infra/local`: a one-node kind cluster with Envoy Gateway as the entry point on `127.0.0.1:8000`; `make cluster-up` and `make cluster-down`; `cluster.yml` creates it in CI too; ADR-0008 on Gateway API instead of an Ingress controller |
| 2 | `feat/2-postgres-cnpg` | Postgres 17 run by the CloudNativePG operator, installed with the cluster; `deploy/charts/fleetops-postgres` per environment, in namespaces that enforce the restricted pod security profile; the credentials are generated by the operator in the cluster, never stored in git. First, because the service charts cannot be tested without a database |
| 3 | `feat/3-helm-charts` | `deploy/charts/fleetops-service`: one chart with a values file per service, with Deployment, Service, HTTPRoute, ConfigMap, probes, resource requests and limits, HPA, and the same non-root security settings as the images; `cluster.yml` lints them, installs them on kind in CI and runs the acceptance suites against them |
| 4 | `feat/4-argocd-gitops` | Argo CD; `deploy/gitops` as app-of-apps: platform apps (Envoy Gateway, CloudNativePG) and FleetOps per environment, with `dev`, `staging` and `prod` values; `make gitops-bootstrap`, the one step that is run by hand, once per cluster |
| 5 | `ci/5-image-promotion` | after a merge, CI moves `dev` to the new image (`:sha-<commit>`); `make promote FROM=dev TO=staging` opens the promotion pull request; ADR-0009 on how a new image reaches `dev` |

## Decisions to make on the way

Each one is made with evidence in the package that needs it and recorded as an
ADR, the way Phase 3 handled its tool choices.

- **The entry point (ADR-0008, package 1): decided.** The roadmap says "an
  ingress controller". The usual choice, ingress-nginx, was retired in March
  2026 and gets no more fixes. The Gateway API, the successor to Ingress, with
  Envoy Gateway as its implementation; the charts ship an `HTTPRoute` instead of
  an `Ingress`.
- **How a new image reaches `dev` (ADR-0009, package 5).** Either CI writes the
  new tag into `deploy/gitops/dev` after the images are published, or Argo CD
  Image Updater watches GHCR and writes it back. Both keep git as the record of
  what runs. The first keeps all moving parts in one workflow; the second is
  the pull model Argo CD is built around. Decided by trying both in package 5.
- **Where `staging` runs until Phase 6.** The roadmap puts `staging` on AKS and
  `prod` on STACKIT, and neither exists before Phase 6. The recommendation is
  `staging` as a second namespace on the kind cluster until then, so promotion
  by pull request can be practised now. `prod` has its values file, but no
  Argo CD application until Phase 6.

## How the local cluster fits together

```
GitHub ──────────────────────────────── kind cluster (Colima, on the Mac)
                                        │
main ──► release.yml ──► GHCR images    │  argocd        polls the repo, syncs
   │                          ▲         │  envoy-gateway the dashboard and API on localhost
   └──► CI bumps dev tag      │ pull    │  cnpg-system   the Postgres operator
        in deploy/gitops/dev ─┼─────────┤  fleetops-dev      web-ui, fleet-api, telemetry-ingest,
                              │         │                    vehicle-sim, Postgres, smoke Job
                              └─────────┤  fleetops-staging  the same, promoted by pull request
```

Argo CD pulls from GitHub, so nothing on GitHub needs to reach the laptop:
no inbound ports, no runner on the Mac. The cost is a delay of up to Argo CD's
polling interval (three minutes by default) between a merge and the sync.

## Constraints

- **No secrets in git.** Argo CD reads the private repository with a read-only
  deploy key, and the cluster pulls from GHCR with a token that can only read
  packages. Both are created by `make gitops-bootstrap` from local files and
  `gh`, and live only in the cluster. Database passwords are generated by
  CloudNativePG.
- **The same rules as the images.** Containers run as uid 10001, non-root,
  with a read-only root filesystem where the service allows it, no privilege
  escalation, and resource limits. The Trivy config scan in `security.yml`
  already reads Helm charts and fails on HIGH findings.
- **The laptop is the budget.** The Mac has 8 GiB of memory in total, and
  Colima's VM (4 CPUs, 8 GiB) can claim all of it, next to macOS. So the
  cluster has one node, every component asks for little, the Compose stack is
  stopped while the cluster runs, and each package measures what it adds
  (`docker stats` in `cluster.yml`). Whether `staging` fits beside `dev` is
  decided on those numbers.
- **Same tests, new target.** The acceptance suites run unchanged against the
  cluster: they already take their URLs from `FLEET_API_URL` and
  `TELEMETRY_URL`, and they import no service code.

## Done when

- [ ] `make cluster-up` and a one-time `make gitops-bootstrap` give a cluster in
      which Argo CD runs every component from git
- [ ] Merging a change to `main` results in the new version running in `dev`,
      with the post-sync smoke test green and no manual `kubectl`
- [ ] Promotion to `staging` is a pull request, and reverting it rolls
      `staging` back
- [ ] Every chart passes `helm lint` and the Trivy config scan, and installs
      on kind in CI with the acceptance suites passing against it
- [ ] No secret in git: repository access, registry access and database
      passwords exist only in the cluster
- [ ] ADR-0008 and ADR-0009 record the decisions
- [ ] `docs/RUNBOOK.md` is written
- [ ] Tag `v0.4.0` via release-please
